# How Thido uses Auth.js

## Responsibilities

Auth.js handles provider sign-in, OAuth callbacks, encrypted session cookies, session decoding, and sign-out. Prisma remains the source of truth for users and linked OAuth accounts. Thido adds its own password hashing, email verification, password-reset tokens, authorization checks, and user settings.

The primary configuration is `src/lib/auth.ts`. It exports:

- `handlers`, mounted by `src/app/api/auth/[...nextauth]/route.ts`;
- `auth()`, used to read and validate the current session on the server;
- `signIn()`, used by login Server Actions;
- `signOut()`, used by sign-out forms.

## Providers

### Google

The Google provider uses `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Auth.js completes the OAuth exchange and the Prisma adapter stores the provider identity in `Account`, linked to a `User`.

The production callback URL is:

```text
https://<production-domain>/api/auth/callback/google
```

### Email and password

The credentials provider validates the submitted values with Zod, applies IP and IP-plus-email rate limits, looks up the normalized email, and verifies the scrypt password hash. Password users must have a non-null `emailVerified` timestamp before Auth.js will create a session.

Plaintext passwords are never persisted. The `User.passwordHash` column stores a salted scrypt result generated by `src/lib/password.ts`.

### Local test provider

When `ENABLE_TEST_LOGIN=true` and `NODE_ENV` is not `production`, a test-only credentials provider is added. Production has a hard code-level guard, so this provider cannot be enabled there merely by setting the environment variable.

## Prisma adapter

`@auth/prisma-adapter` connects Auth.js to the `User`, `Account`, `Session`, and `VerificationToken` models in `prisma/schema.prisma`. Thido currently uses JWT sessions, so the `Session` model is present for adapter compatibility but normal application sessions are stored in encrypted cookies rather than as database session rows.

## JWT sessions

The configuration uses:

```ts
session: { strategy: "jwt" }
```

On sign-in, the JWT callback adds the database user ID and the user's `sessionVersion` to the encrypted token. On later requests it checks that:

1. the token contains a user ID and session version;
2. the user still exists in the current database;
3. the database session version still matches the token.

If any check fails, the callback returns `null`, making the session invalid. This prevents an old cookie from referring to a user removed during a database change. A password reset increments `sessionVersion`, which invalidates existing sessions on their next validation.

The session callback exposes only the user ID alongside Auth.js's normal session-safe user fields. Password hashes and authentication tokens are never placed in the browser session.

## Route protection

`src/proxy.ts` performs the early navigation check. Unauthenticated page requests are redirected to `/login` with a safe callback path and a visible notice. Public authentication pages and API routes are allowed through.

Proxy is not the final authorization boundary. Server Components call `auth()` again before reading user data, Server Actions authenticate before mutations, and Route Handlers return structured `401` responses when no valid session exists. Ownership queries include the authenticated user ID.

Administrator authorization is separate from authentication. `src/lib/admin.ts` checks the authenticated email against `ADMIN_EMAILS`; authenticated non-admin users are sent to `/forbidden`.

## Email verification

Password registration creates an unverified user, issues a random 32-byte token, stores only its SHA-256 hash in `AuthToken`, and sends the raw token in a Resend link. The link expires after 24 hours and is single-use. Successful verification sets `User.emailVerified`.

Google verification is handled through Google's verified identity information and the Auth.js provider flow.

## Password reset

Reset requests always show the same response whether an account exists or not. Eligible password accounts receive a single-use link that expires after one hour. A successful reset replaces the scrypt hash, deletes outstanding authentication tokens, and increments `sessionVersion`.

## Required environment variables

```text
AUTH_SECRET
NEXTAUTH_URL
GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET
RESEND_API_KEY
AUTH_EMAIL_FROM
```

`AUTH_EMAIL_FROM` must use a domain verified in Resend for production delivery.

## Sign-out

Ordinary sign-out clears the current browser's Auth.js session cookie and
redirects to `/login?notice=signed-out`; other browsers retain their sessions.
The Settings sign-out-all-devices action and password reset increment
`User.sessionVersion`, invalidating existing JWTs on subsequent validation.
